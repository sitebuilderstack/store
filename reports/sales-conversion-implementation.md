# Sales and conversion implementation

September 2026.

## Action 4 — Complete Site Builder Stack

### What shipped

A fourth product at `/products/complete-site-builder-stack`, **$149**, SKU
`SBS-CCSTACK-V1`, active and published to the Online Store.

It contains the three existing products delivered as **three separate downloads
on one order** — not a fourth combined archive. That was the deciding design
choice. A combined ZIP would have to be rebuilt and its checksum republished
every time any of the three changed, and the version it contained would become a
fourth number capable of disagreeing with the other three.

### Every price is read from the live products

`sections/sbs-bundle-value.liquid` renders the comparison. It resolves each
component through `all_products[handle]`, sums the real prices, and subtracts the
bundle's own price. Nothing is typed into a setting.

Currently: $99 + $39 + $59 = **$197** separately, **$149** together, **$48** less.

If **any** component is unavailable the entire section is suppressed rather than
shown with a smaller total, because a saving computed from two of three products
would overstate the bundle's value quietly.

### The honesty constraints, enforced rather than intended

`scripts/publish-bundle-product.py` refuses to publish if the description:

- states any money at all — the live section owns every price, and a number typed
  into a description is one that goes stale the first time a price changes;
- contains a struck-through "was" price, a percentage off, an urgency claim, a
  scarcity claim, a threatened price rise, or a claimed value;
- misstates the file count or word count against the three product directories;
- fails to link to all three components;
- or names a bundle price **at or above** the separate total.

All six guards were control-tested by breaking the description on purpose and
watching each fire, then restoring it and watching them go quiet.

$197 is never presented as a former price. The store has never charged it in one
transaction, so calling the difference a discount would fabricate one — the exact
pattern the conversion toolkit prohibits by name, on the storefront that sells it.

### The product image

Generated by `scripts/generate-bundle-image.py`, in the same tokens, mark and
grammar as the other three product images so all four read as one family.

It could not reuse the existing generator: that one draws a single bundle's
module grid, and a grid of 267 files would be unreadable. This draws the three
products as three panels in lifecycle order, which is what the bundle actually
sells.

Every number on it — 44 modules, 267 files, and the per-product counts — is
counted from the product directories at generation time. An image is the one
place a stale count is invisible to every text-based check.

**Prices are deliberately not drawn.** An image is not regenerated by a price
change, so a picture asserting $197 after a price moved would be a misleading
price claim that no check could see.

Attached with alt text that describes the three panels and their counts, so the
information in the image is available to anyone not seeing it.

### Where the bundle appears

| Placement | Form |
| --- | --- |
| Header Products menu | Fourth slot, resolved live |
| Homepage | A single CTA after the three-product row |
| Each product page | A third card in that page's "other products" row |
| Every guide | One line under the product CTA, with both figures |
| Footer | Products column |
| `/collections/all` | Automatically, and the meta description now counts 4 |
| `agents.md` | Full entry, with the total explained |

The homepage keeps its **three**-product lifecycle row. A fourth card would have
wrapped 3+1 in a three-column grid and diluted the Build → Rank → Convert
explanation, which is the row's actual job. The bundle gets its own compact CTA
beneath instead.

The guide line is rendered only when the bundle resolves **and** is genuinely
cheaper than the components. Control-tested by pointing it at a non-existent
component: the line disappeared rather than claiming a saving it could not
verify.

### `agents.md` said "There is no bundle"

It did, in those words, instructing agents to tell users otherwise. Corrected,
and the auditor that caught it now verifies that a stated **total** equals the sum
of the live component prices — so if any price changes, the $197 stops matching
and the check fails. Control-tested by changing it to $200.

## Action 6 — Segmented lead funnel

### Segmentation

The signup form now asks one question — build, rank, or convert — using radio
inputs named `contact[tags]` on Shopify's **native customer form**. The selected
option submits `claude-md-kit,goal-build` (or `-rank` / `-convert`), so the answer
lands on the customer record where an email platform can already read it.

No JavaScript, no second platform, no new identifier. The first option is
pre-selected so a submission without a deliberate answer still lands somewhere
real.

### Three sequences

`docs/growth/emails/segmented/` holds `build.md`, `rank.md` and `convert.md`, six
emails each, ~3,900 words total, following Deliver → Teach → Workflow → Worked
example → Matching product → Bundle.

Four of six in each sequence are worth reading by someone who never buys, which
is the only reason the fifth and sixth get opened. Email 6 states both figures and
never calls the difference a discount.

**None of it is configured or sending**, and the README says so first rather than
last. Three blockers are listed, the first of which is that the signup form has
never produced a subscriber.

### Analytics

New events: `lead_segment_build` / `_rank` / `_convert`, `product_sample_viewed`,
`bundle_cta_clicked`, `readiness_product_clicked`. All go through the existing
`Shopify.analytics.publish` layer — no second vendor, no extra request.

Four separate names for the four product-click placements on purpose. Merging
them would make all four unreadable, and the question worth answering is which
placement sells.

## The blocking problem, stated plainly

**The bundle is purchasable and cannot be delivered.** No files are attached to
it. The same is true of the SEO and conversion toolkits.

The Admin API cannot see whether a file is attached in the digital-delivery app;
only a fulfilled paid order proves it. `scripts/verify-digital-delivery.py` fails
on exactly this and now fails for three products instead of two.

That is a store-owner action and nothing in this cycle changes it.
