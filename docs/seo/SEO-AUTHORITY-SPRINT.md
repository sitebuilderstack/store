## 1. Refund policy contact address

**The change.** `admin@lofiskunk.com` → `admin@sitebuilderstack.com`.

**Where it lived.** Not in this repository. `grep -rn lofiskunk .` returned zero matches;
the policies are stored in Shopify. `scripts/fix-policy-contact.py` rewrites them through
the Admin API (`shopPolicyUpdate`, which keys on `type`, not `id`) and then re-reads from
a fresh query to verify rather than trusting the mutation response.

**Scope.** Four policies carried the legacy address, not one:

| Policy | Occurrences | Result |
| --- | --- | --- |
| Refund policy | 2 | updated, verified live |
| Terms of service | 2 | updated, verified live |
| Shipping policy | 2 | updated, verified live |
| Contact information | 2 | updated, verified live |
| Privacy policy | 0 in the body | see below |

**Live verification.**

```
$ curl -s https://sitebuilderstack.com/policies/refund-policy | grep -o 'admin@[a-z.]*' | sort -u
admin@sitebuilderstack.com
```

**One outstanding item, and it needs the admin UI.** The privacy policy is generated by
Shopify and interpolates the store contact email at render time, so the legacy address
still appears there even though it is nowhere in the stored body. There is no Admin API
mutation for that field — schema introspection returns only `shopLocaleDisable`,
`shopLocaleEnable`, `shopLocaleUpdate`, `shopPolicyUpdate`, `shopResourceFeedbackCreate`
and `shopifyPaymentsPayoutAlternateCurrencyCreate`.

**Manual step:** Shopify admin → Settings → Store details → **Store contact email** →
set to `admin@sitebuilderstack.com`. That one field also feeds customer-facing emails and
any other auto-generated policy text. The store phone number and address on that screen
feed the same template.

**Pipeline.** Markdown in `resources/` is the single source of truth. `scripts/md2html.py`
converts it to the site's existing markup conventions (`.sbs-table`, `.sbs-checklist`,
`.sbs-toc`), deliberately supporting only the subset used — a general-purpose converter
would emit markup the stylesheet does not know about. `scripts/publish-resources.py`
publishes by handle, idempotently, and sets the SEO metafields.

**Why the checklist markers are CSS pseudo-elements, not `<input type="checkbox">`.**
These are documents to read and copy, not forms. Real checkboxes would add dozens of
unlabelled controls to the tab order for no benefit, and their state would be lost on
reload.

### GitHub starter kit — prepared, **not published**

## 3. Author entity

| Change | Where |
| --- | --- |
| All 19 guides attributed to James Joyner IV | `content/articles.json` → `author`, republished |
| Byline links to the author page | `sections/sbs-article.liquid` |
| Author box closes each guide | `snippets/sbs-author.liquid` |
| `Person` node with a stable `@id` | `snippets/sbs-schema.liquid` |
| `ProfilePage` + `Person` on `/pages/about` | same |
| `BlogPosting.author` is that `Person` | same |
| `Organization.founder` points at it | same |

The Person `@id` is `https://sitebuilderstack.com/pages/about#person` everywhere, so the
article author, the About page's `mainEntity` and the organisation's founder are one
entity rather than three lookalikes.

**Conditional attribution.** The author box and the `Person` node render only when
`article.author == 'James Joyner IV'`. An article genuinely written by someone else falls
back to an `Organization` author. Both branches are evidenced: the Organization branch is
what every guide rendered before this change, captured live.

**`sameAs` is empty, deliberately.** The theme carried four social settings, all set to
the literal placeholder `#` from the purchased theme. No verified profile for the site or
the author was available, so nothing was invented. Two new theme settings under
**Site Builder Stack — SEO** (`org_sameas`, `author_sameas`) accept one URL per line and
emit `sameAs` when filled. They ship empty. A `sameAs` pointing at a 404 is worse than no
`sameAs`.

**Claims.** The author box states 25 years in technology and the technologies listed on
the About page, and nothing beyond them. No certifications, no employers, no client names.

**Added this sprint:** `Person`, `ProfilePage`, `Blog`, product breadcrumbs, blog
breadcrumbs, three-level resource breadcrumbs, `Organization.logo`,
`Organization.founder`, `@id` on `BlogPosting` and `Blog`.

**Deliberately absent, with reasons written into the template:**

- **No `Review` / `AggregateRating` / `rating` anywhere.** There are no reviews. Adding
  it is a guidelines violation and a manual-action risk.
- **No `MerchantReturnPolicy`.** Refunds are decided case by case. None of schema.org's
  return categories (`MerchantReturnFiniteReturnWindow`, `MerchantReturnUnlimitedWindow`,
  `MerchantReturnNotPermitted`) describes that honestly, and inventing a window to satisfy
  a validator would put the markup in conflict with the published policy.
- **No `SearchAction`.** The store has no site search worth declaring.
- **No `sameAs`** until real profiles exist. See above.

**Validation.** `scripts/audit-seo-site.py` parses every `application/ld+json` block in the
rendered HTML of all 44 crawled pages. No parse failures. No page carries two entities of
the same type.

### Merchant Center — **not eligible enough to act on**

Google's [unsupported Shopping content](https://support.google.com/merchants/answer/6150006)
policy lists, verbatim, "eBooks and digital books (not including audiobooks)" with the
examples "PDFs, EPUB books, MOBI", and separately lists services as "labour, time, effort,
expertise or actions which don't result in ownership of a tangible product".

The Launch System is a downloadable archive of documents. It sits close enough to both
categories that eligibility is genuinely uncertain, and misrepresentation is the most
common cause of Merchant Center suspension.

**Decision: no feed, no merchant markup, no `MerchantReturnPolicy`.** None of this affects
organic search. Revisit only if Google's policy changes or a support answer confirms
eligibility for this specific product.

## 7. Audit tooling, and why its passes can be trusted

Four of this project's own checkers have previously reported success on exactly the
condition they existed to catch. Every check touched in this sprint was therefore
control-tested in both directions.

| Check | Proved it fires on | Proved it stays silent on |
| --- | --- | --- |
| Tap-target size (SC 2.5.8) | a 21×11 nav link, a 136×19 standalone list link | an in-sentence link (the spec's inline exception) |
| Accessible name | a focusable link inside `aria-hidden` | a correctly `tabindex="-1" aria-hidden` thumbnail |
| Entity leak in meta tags | `content="… &amp;mdash; …"` | `content="… — …"` |
| Tag-archive noindex | tag URLs get the tag | the blog index does not |
| Collection noindex | `/collections/frontpage` gets it | the product page does not |
| `audit-seo-site.py`, all 11 rules | one crafted failure each, via `--self-test` | a clean record, a noindex record, a policy alias |

```
$ python3 scripts/audit-seo-site.py --self-test
  404                    fires
  duplicate title        fires
  duplicate description  fires
  missing description    fires
  two h1                 fires
  no canonical           fires
  canonical mismatch     fires
  entity leak            fires
  missing og             fires
  no twitter card        fires
  invalid JSON-LD        fires
  clean record           silent
  noindex exempt         silent
  policy alias -> note   correct

self-test passed
```

One bug was introduced and caught during the sprint: adding `og:description` to the policy
layout reintroduced the `&amp;mdash;` double-escape the site had fixed before, because the
description was captured with an HTML entity and then run through `escape`. Fixed with a
literal em dash and a comment; the entity-leak detector was verified against both strings.
