Why this exists

Twenty-five years of infrastructure work leaves you with a particular instinct: most tools fail not because they are weak but because nobody wrote down how to use them properly. Claude Code is genuinely capable. What is missing is the operational layer around it — the constraints, the checks, the order of work, the things you verify before calling something finished.

That layer is what I do for a living, applied to a different kind of system. The Claude Code Website Launch System is that discipline written down.

Where the habits come from

The skills in that table are not a list of things I have read about. They describe the work: building and running production systems, and the operational discipline that goes with it.

  • Systems and infrastructure engineering. Linux as the substrate, and the assumption that anything not written down will be done differently by the next person who touches it.
  • Cloud and orchestration. Kubernetes and OpenStack — platforms where a change lands across many machines at once, so "it worked on mine" stops being a defence.
  • Automation and infrastructure as code. Ansible and Terraform. The reason I care so much about reproducibility: a build that only works when a particular person runs it is not a build.
  • CI/CD. GitLab pipelines. This is where the habit of making a check fail on purpose comes from — a green pipeline that has never gone red is not evidence of anything.
  • Containers. Docker, mostly as a way of removing "works here" from the conversation.
  • Observability. Victoria Metrics, Prometheus, Grafana. Instrumenting systems so they can tell you whether they are working, rather than being asked.
  • Python. The language most of the automation is written in, including the scripts that audit this site.
  • AI-assisted development. Claude Code and MCP, applied to real production work rather than demos. This store is the current example.

The through-line is the same in all of them. Infrastructure work teaches you that the dangerous failure is not the one that shouts. It is the one that reports success.

How this content is written and checked

Site Builder Stack publishes technical guides, and it is worth being explicit about what that does and does not mean.

  • Written against primary sources. Behaviour of Claude Code, Shopify and Google is taken from their own documentation, and each guide links the pages it drew on so you can check.
  • Measured where measuring is possible. Claims about how this store behaves — canonical tags, redirects, response codes, structured data — come from fetching the URL and reading what came back, not from reading the template.
  • No invented numbers. There are no search volumes, difficulty scores, conversion rates or customer counts anywhere on this site, because I have no data source for them. If you see a specific figure, it came from a request.
  • Production-oriented. Every guide ends with something you can verify rather than something you are asked to believe.
  • Updated when the tooling moves. Claude Code changes quickly. When something here goes out of date, it gets corrected rather than quietly left.

What I am not claiming: that I have personally run every command in every guide on every platform. Where something is drawn from documentation rather than from my own terminal, the guide says so and links the source. If you find something that is wrong, I would rather hear about it than have it sit there.

This site is the demonstration

The most honest thing I can tell you about the method is that this storefront was built with it, and it was not smooth. Some of what went wrong:

  • A primary call-to-action rendered invisible — text at 1:1 contrast against its own background, because a generic link rule outranked the button rule by a single point of CSS specificity. Nothing in the source looked wrong.
  • The homepage shipped with its <title> set to the raw .myshopify.com domain, because the theme fell back to it when a setting was never filled in. It looked completely normal in a browser.
  • Every call-to-action on every non-home page was dead — they linked to a fragment that only exists on the homepage. No error, no navigation, just a click that did nothing.
  • The store spent a period unable to accept payments at all, displaying "This store can't accept payments right now" at checkout. That notice is injected by JavaScript and absent from the initial HTML, so every automated check reported a healthy checkout.
  • A test order fulfilled correctly and delivered nothing, because it was placed with a phone number and no email address. Every status Shopify reported said success.

The full account of that build, with the mechanism behind each failure and the evidence, is in the Site Builder Stack case study.

I mention these because they are the argument for the product. None of them were visible to someone looking at the site. All of them were found by fetching URLs and measuring what came back — which is what the checklists and audits in the Launch System exist to make routine.
