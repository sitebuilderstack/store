# Website scope of work — template

Fill in every section. Where a fact is not yet known, write **TBD** and name who
owes it and by when. A TBD is a visible gap; a guess is an invisible one.

**This is an operational planning document, not a legal agreement.** It records
what will be built, by whom, and how both sides will know it is finished. It is
not a contract, and it is not a substitute for one. Have a solicitor look at
your contract; use this to stop the argument that a contract cannot settle.

Free to use and adapt. From [SiteBuilderStack](https://sitebuilderstack.com).

---

## 1. Project summary

```
Client:            [legal name]
Project:           [short name]
Prepared by:       [you]
Date:              [date]
Version:           [v1, v2 — this document will change]
Approver:          [ONE named person who can say yes]
```

One named approver. Not "the team", not "the owner and the manager". If two
people can approve, two people can disagree after the fact.

## 2. Objectives

Two or three. Each must be something the client would recognise as success.

```
1. [Objective, in the client's words, with a number if one exists.]
2. [...]
```

Avoid objectives you cannot influence ("rank first for physiotherapy"). Write
the thing the website can actually do.

## 3. Deliverables, with counts

```
| # | Deliverable | Count | Notes |
|---|-------------|-------|-------|
| 1 | [Thing]     | [n]   | [what "one" of these includes] |
```

**Counts are the whole point of this section.** "A website" is not a
deliverable. "Nine pages, of which three share one service-page layout" is.

## 4. Page and content inventory

Every page, listed. This is the document both sides count against.

```
| Page | Layout | Content source | Notes |
|------|--------|----------------|-------|
```

## 5. Functional requirements

What the site must *do*, each written so it can be demonstrated.

```
| # | Requirement | How it will be demonstrated |
|---|-------------|------------------------------|
```

If you cannot write the second column, the requirement is not yet a
requirement.

## 6. Exclusions

The most valuable section in the document. List what is **not** included,
especially things discussed and not agreed.

```
- [Thing], not included in this project.
- [Thing mentioned on the call as "maybe later"], not included.
```

Anything a client said "maybe" about belongs here by name.

## 7. Client responsibilities

```
| # | What the client provides | By when | If it is late |
|---|--------------------------|---------|---------------|
```

The third column is not a penalty. It is the honest statement that a dependency
slipping moves a date, so nobody is surprised when it does.

## 8. Dependencies

Things outside both parties' control: DNS access, a third-party account, a
provider's approval queue.

## 9. Milestones and their assumptions

```
| Milestone | Target | Assumes |
|-----------|--------|---------|
```

**Every date carries its assumption.** A date without one is a promise about
things you do not control.

## 10. Review rounds

```
Rounds included per deliverable: [n]
What a round is:  one consolidated set of feedback from the approver.
Not a round:      typo fixes, or anything that was wrong against this scope.
Beyond [n]:       handled as a change request (section 12).
```

Define what a round *is*. "Two rounds of revisions" without a definition is two
different numbers to two people.

## 11. Acceptance criteria

Observable checks. Someone who was not in the meetings must be able to run them
and get the same answer.

```
| # | Criterion | How it is checked |
|---|-----------|-------------------|
```

Good: "The enquiry form sends to [address]; a test submission is received and
shown to the approver." Bad: "The form works."

## 12. Change-request process

```
1. Request is written down (email is fine).
2. It is compared against this document and classified:
   IN SCOPE — already covered, will be done, no change.
   AMBIGUOUS — this document is unclear; clarified and the scope updated.
   OUT OF SCOPE — not covered; estimated separately.
3. Out-of-scope items get a written estimate: effort, cost, schedule impact.
4. Nothing starts until the approver says yes in writing.
```

Classify before pricing. Some requests are already in scope, and a process that
prices everything teaches a client to stop asking.

## 13. Handoff

```
- [ ] Credentials transferred by [route]
- [ ] Deployment steps documented
- [ ] Decisions log handed over
- [ ] What the client can safely change themselves
- [ ] What they should not change
- [ ] Support after handoff: [what, for how long, or "none"]
```

## 14. Open questions and assumptions

```
### Open questions
| # | Question | Owner | Needed by |

### Assumptions
| # | We have assumed | If wrong |
```

**Do not delete this section when it empties.** An empty open-questions table
with a date on it is evidence. A deleted one is nothing.
